# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Bun + Turborepo monorepo: `apps/web` (TanStack Start on Cloudflare Workers + D1), `packages/db`, `packages/services`.

## Commands

- `bun test` (not `bun run test`) runs every test directly. One file: `bun test packages/services/src/bookings.test.ts`. By name: `bun test -t "<pattern>"`.
  Why: `bun run test` goes through turbo and is slower; the README and scripts assume the bare form.
- `bun run check` before finishing: lint (Ultracite/Biome) plus typecheck in every package. `bun run fix` to format.
  Why: the husky pre-commit hook runs `ultracite fix` and fails the commit on unfixable issues.
- `bun run dev` applies migrations and seed data itself; don't run `db:apply`/`db:seed` first.
  Why: it already does both against a local DB in `apps/web/.wrangler`. Delete that folder to reset.
- `db:*:remote` and `deploy` touch the real Cloudflare account. Never run them unasked.

## Layering (route → tRPC router → service → `@repo/db` query)

- Put validation and business rules in `packages/services`, never in tRPC routers or `@repo/db`.
  Why: routers must stay thin (input schema from the service, one service call), and the db layer is deliberately validation-free. Services also re-parse input so non-tRPC callers are safe.
- Services and db functions take a drizzle instance as a parameter. Never read `env`, bindings or the request inside them.
  Why: the same code runs on D1 in prod and `bun:sqlite` in tests. `apps/web/src/server/trpc/context.ts` is the only place `env.DB` is read.
- A new service must also be added in `context.ts`.
  Why: nothing else wires it onto `ctx.services`, and the omission only shows up at runtime.
- Throw `ServiceError` subclasses (`NotFoundError`, `ValidationError`, `ConflictError`, `ForbiddenError`), not plain errors.
  Why: `init.ts` maps them to 404/400/409/403; anything else becomes a 500.
- Mutations take the acting member id first and check it with `requireMember`/`requireAdmin`.
  Why: there is no auth. `userId` in the tRPC context is always null, and the actor arrives as `actorId` in the input.
- Query functions return plain JSON shapes (string ids, ISO dates), not drizzle row types.
  Why: results are serialized by tRPC and the row type is private to the module.

## Module boundaries

- No barrel files. Each new module is `src/<name>.ts` plus its own line in that package's `exports`.
  Why: imports are `@repo/db/<table>` / `@repo/services/<module>`; a module missing from `exports` can't be imported.
- Browser/React code may import only `@repo/db/shared`. Put anything the UI needs (types, limits) in `packages/db/src/shared.ts`.
  Why: every other entry imports drizzle, which then leaks into the client bundle.
- Use `getTrpc()` from `src/integrations/trpc/client.ts` in loaders and handlers.
  Why: it runs the router in-process during SSR, so loaders don't fetch their own Worker.

## Schema changes

- Edit `packages/db/src/schema.ts`, then run `bun run generate` in `packages/db`. Commit `migrations/` including `migrations/meta/`.
  Why: drizzle diffs against the snapshot in `meta/`; without it the next generate recreates the tables.
- Don't hand-edit `migrations/` or apply them with drizzle-kit. Wrangler applies them.
  Why: `wrangler.jsonc` points `migrations_dir` at that folder, and D1 tracks applied migrations itself.
- Seed data lives in `packages/db/seed.sql`, not in a migration.
  Why: it must be safe to re-run, and the deployed app has no members (so nobody can book) until it's loaded.

## Tests

- Use `createTestDatabase()` from `@repo/db/testing` and `packages/services/src/fixtures.ts` (small team, two rooms). Don't mock the db.
  Why: it applies the real migrations, so a test covers service, queries and schema together.

## Don't edit

- `apps/web/src/routeTree.gen.ts` (generated by the router) and `apps/web/src/components/ui/*` (vendored shadcn).
- `worker-configuration.d.ts` (generated by `bun run cf-typegen` from `wrangler.jsonc`).
